## 一、Codex 是什么


Codex 桌面版的定位不是普通聊天机器人，而是可以直接在电脑上执行动作的 Agent。界面通常是左侧对话线程、右侧实时预览面板：你能看到它正在改哪些文件、写了什么代码、点了哪个按钮。

任务组织上，它用 **Project（项目）** 做主容器。创建项目时核心会配置三块：

- 项目名称
- 文件路径
- 权限级别（只读 / 允许改文件 / 允许执行命令）

每个项目里可以开多条 Chat，对应不同子任务，产出的文件也会归档在项目目录，方便回看和追溯。

最关键的是：Agent 在后台跑任务时，你可以继续做别的事，不会被“必须盯着它”卡住。

此外，Codex 支持 **Fork（分叉）** 对话。你要验证另一条实现路径时，不用重开项目，直接从当前节点分叉，两个方向独立推进。

## 二、Plugin 与 Skill：怎么把能力边界往外推

Codex 的扩展主要靠两层：

- **Plugin**：连接外部系统（例如 Gmail、Calendar、Figma、Notion），让 Agent 能跨工具读写和操作；
- **Skill**：可复用的任务模板，把你高频流程封装成一条可反复调用的能力。

实操里演示了几类典型 Skill：

- YouTube Researcher：抓取视频转写并生成总结
- Paper Designer：生成无背景设计图
- Word Doc：输出标准化文档

你只要在指令里调用对应 skill 名称，就能复用整套流程。

进一步还能做 **Automation（自动化）**：把多个 Skill 串成定时任务。例如按周自动抓频道更新、汇总结果并发送邮件，整个链路无需人工反复介入。

## 三、实战重点：一个下午并行推进六个任务


案例里最有代表性的部分，是同时推进六条工作线：移动应用、落地页、宣传动画、数据库、设计稿、TestFlight 发布。

方法不是把所有事塞到一个对话，而是每个任务开独立 Chat，让不同 Agent 实例并发处理。

几个高价值技巧：

1. **截图沟通优先**：给局部截图并指定改动区域，通常比文字描述更快、更准确。
2. **等待期切换任务**：一个 Agent 在编译时，立刻切到另一个任务继续推进，减少空转时间。
3. **Prompt 中串 Skill**：把“调研 → 产出文档”这类链路一次性说清，减少手工拼接步骤。

核心思路就是：你做调度，Agent 做执行。

## 四、数据库、落地页与视频生成：端到端闭环怎么跑


在 App 页面完成后，数据层常常是最大阻塞点。案例里让 Agent 根据需求评估后，选择了 Supabase（Postgres 体系），并产出建表语句与 OAuth 相关接入代码。

其中一个高频收益点是：像 Google OAuth 这类流程，Agent 可以把控制台操作路径拆成明确步骤，减少你来回查文档的成本。

落地页部分则强调了一个实践经验：不要只给“做个好看页面”这种抽象指令，最好提供明确参考风格（如具体网站或设计样例），输出稳定性会明显更高。

视频制作用 Remotion 这类 React 视频方案时，很多过去要手动做的动效，也可以通过几轮对话快速迭代出可用版本。

## 常见问题

### Q1：这篇案例最值得学的不是某个按钮，而是什么？
A：是任务编排思路。把复杂目标拆成并行子任务，用多个 Agent 同时推进，而不是在单对话里硬撑到底。

### Q2：Plugin 和 Skill 的区别怎么记最简单？
A：Plugin 负责连外部系统，Skill 负责复用你的工作流。一个扩边界，一个提复用。

### Q3：为什么截图沟通这么重要？
A：因为 UI 和交互改动很多是视觉问题，截图能减少描述歧义，反馈回路更短。

### Q4：单人开发也需要多 Agent 并行吗？
A：需要。只要任务里有“等待时间”（编译、构建、上传），并行就能显著减少空转。
