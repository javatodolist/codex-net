## 【2026 最新】免费使用 Codex 的 4 种方法

### 方法 1：通过 ChatGPT 付费方案实现“准免费”使用

如果你已经订阅了 ChatGPT Plus、Pro、Team 或 Enterprise，那么可以**不额外购买 Codex 服务**，直接使用 Codex CLI。

原文提到，这套联动机制是在 2025 年 8 月 GPT-5 发布后引入的。对于本来就在付费用 ChatGPT 的人来说，这基本就是最低折腾成本的方案。

原文给出的价格信息是：

- **ChatGPT Plus**：20 美元/月
- **ChatGPT Pro**：200 美元/月

同时，不同套餐对应的使用上限也不一样。文中给出的参考范围是：

- **Plus**：每 5 小时大约 30 到 150 条消息
- **Pro**：每 5 小时大约 300 到 1500 条消息

如果你是高频写代码、经常要让 AI 连续改文件、跑多轮交互的用户，Plus 能不能够用，得看你的实际强度；Pro 则更适合重度用户。

落地上反而没什么复杂的。核心步骤就是先完成账号登录，然后在 CLI 里直接进入 Codex：

```bash
codex
```

原文的结论很明确：如果你本来就是 ChatGPT 订阅用户，这条路往往是最省事的。它的优点不是“绝对免费”，而是**不需要你再为 Codex 单独付第二次钱**，整体体验也最接近开箱即用。

### 方法 2：结合 Ollama + 本地 LLM 实现纯免费运行

如果你更看重“完全免费”和“代码尽量别出本机”，那原文更看好 Ollama 方案。

这条路的思路是：把 Ollama 当成你本地的大模型后台，再让 Codex CLI 去调用它。这样你就不用额外买 API，也不用把敏感代码发到云端，对一些内部项目、个人实验仓库或者本地高频试错场景都很合适。

第一步是装好 Ollama 并启动服务：

```bash
brew install ollama
ollama serve
```

接着，根据你的机器性能选模型。原文举了两个例子：

```bash
ollama pull qwen:4b
ollama pull gpt-oss:20b
```

这里的意思很直白：

- `qwen:4b` 更偏轻量，适合机器一般、先求跑起来
- `gpt-oss:20b` 更偏性能，但对本地硬件要求也更高

然后要把 Codex 指到本地 Ollama 服务。原文给出的 `~/.codex/config.toml` 示例是：

```toml
profile = "qwen-4b"

[model_providers.ollama]
name="Ollama"
base_url = "http://127.0.0.1:11434/v1"

[profiles.qwen-4b]
model = "qwen:4b"
model_provider = "ollama"
```

如果你想把上下文窗口再拉大一点，原文还给了一个扩展思路：

```bash
ollama run gpt-oss:20b
>>> /set num_ctx 64000
>>> /save gpt-oss-64k:20b
```

这么做的好处，是能让本地模型在更大的上下文下工作，对多文件理解、较长代码链路分析会更舒服一些。

这条路最大的优点有两个：

- **真正不花 API 钱**
- **隐私更可控**

但代价也很明显：你得自己维护模型、服务和本地性能。要是机器配置比较一般，响应速度和生成质量就别指望和云端顶级模型完全一样。

### 方法 3：活用 Gemini 免费额度

如果你想要更大的上下文窗口，但又不想一开始就上高成本 API，Gemini 免费额度是个很现实的折中方案。

**Gemini 2.5 Pro 的上下文窗口很长**，很适合大规模代码重构、跨文件理解、项目级依赖梳理这类任务。这个点其实挺关键，因为很多 AI 编程场景不是“写一小段函数”，而是“理解整个项目到底怎么连起来”。

这条路的基本步骤是先去 Google AI Studio 申请免费的 API Key，然后把它接进支持多服务商的 Codex CLI 社区分支版本里。

环境变量示例：

```bash
export GOOGLE_GENERATIVE_AI_API_KEY="您的 API Key"
set GOOGLE_GENERATIVE_AI_API_KEY="您的 API Key"
```

原文里的配置示例则是：

```json
{
  "provider": "gemini",
  "model": "gemini-2.5-pro-preview-03-25",
  "apiKey": "您的 Gemini API Key",
  "approvalMode": "auto-edit"
}
```

这里有个细节别忽略：原文提到的并不是 OpenAI 官方那条只连单一服务商的封闭路径，而是**支持 Gemini、Ollama 等多种 AI 服务商的社区分支版本**。也正因为这样，Gemini 这条路才真正可用。

如果你的使用重点是：

- 仓库比较大
- 重构跨度比较大
- 想让模型一次吃进更多上下文

那 Gemini 方案确实会比一些小模型更顺手。

### 方法 4：利用 LM Studio 进行本地化运行

如果你不喜欢全靠命令行折腾，LM Studio 会是一条更友好的路。
**目前最容易上手的图形化本地 LLM 软件之一**。它能提供与 OpenAI 兼容的 API Server，所以很多现有编程工具都能很自然地连上去。

这条路适合两类人：

- 想在本地跑模型，但又不想从头手搓一堆命令
- 想更直观地管理模型下载、加载和服务状态

它的核心价值不一定是“最强”，而是“更省脑子”。尤其是对刚开始接触本地模型的开发者来说，图形化界面能明显降低心理门槛。

## 方案对比与选型建议

原文的态度很明确：没有哪条路能对所有人都最优，关键还是看你最在意什么。

### 如果你已经是 ChatGPT Plus/Pro 用户

那最优先考虑的就是**方案 1**。

原因很简单：你已经付过订阅费了，再单独去折腾其他链路，很多时候是在给自己增加切换成本。登录就能用、性能稳定、配置最少，这三点对日常开发非常重要。

### 如果你最在意隐私和本地可控

那就优先看 **方案 2（Ollama）**。

它最适合不想把敏感代码上传云端、也愿意自己维护本地模型环境的人。机器越强，这条路越香；如果只是轻量试用，也可以先从更小的模型开始。

### 如果你最在意超长上下文

那 **方案 3（Gemini）** 会更值得试。

原文强调的就是这一点：百万级上下文长度对大型仓库理解、跨模块分析非常有帮助。对“要让 AI 看完整个项目”的场景来说，这不是小优势。

### 如果你想尽量降低本地模型的操作门槛

那就看 **方案 4（LM Studio）**。

它不一定是最极客的选择，但对很多开发者来说，能稳定、直观、少踩坑地把本地 AI 环境跑起来，本身就已经很有价值了。
